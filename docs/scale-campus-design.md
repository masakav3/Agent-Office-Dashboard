# Claude Office 规模化设计：园区 · LOD · 按工具分楼

> 状态：**设计稿（待评审）** · 2026-06-07
> 目标读者：claude-office 维护者
> 关联：[debug-parameters.md](debug-parameters.md)（现有调试参数）、[art-pipeline.md](art-pipeline.md)（素材与串色规则）

---

## 0. TL;DR

claude-office 是**面向全公司开发同学的 Agent 看板**，接入工具多样（Claude Code / openclaw / hermes / vscode+claude 插件 / trae / cursor …），**总规模预计 40–50 个并发会话**。

当前的「单一中央中庭 + 房间环绕」布局在 **≤8 间**时最佳，>8 会触发同心外环导致**悬崖式缩放、偏心、房间过小**，且 40–50 间全量精渲会**严重掉帧**。

本设计提出三件事：

1. **按 channel（工具）分楼** —— 每种工具 = 一座主题色统一的「楼/园区分区」，内部由 1..k 个 ≤8 间的庭院组成。
2. **园区 = 庭院的分形** —— 多座楼用同一套环形/网格布局摆在园区里，复用现有 `cellPos`/旋转数学。
3. **LOD 语义缩放** —— 拉远看"状态总览"（色块+状态点），拉近看"完整 3D 办公室"。既保可读性又保帧率。

向后兼容：单工具、≤8 间时退化为**与今天完全一致**的单庭院。

---

## 1. 背景与需求（重新定位）

| 维度 | 早期实现假设 | 真实需求 |
|------|--------------|----------|
| 规模 | 个人 1–8 个会话 | 全公司 **40–50** 并发接入 |
| 来源 | 主要 Claude Code | **多工具混合**：claude code / openclaw / hermes / vscode+claude / trae / cursor / … |
| 关注点 | 看"每张桌子在干嘛" | 一眼掌握"**全局状态分布**" |
| 性能 | 几十个网格对象 | 数百角色 + 家具 + Bloom，**必须分级渲染** |

**结论**：8 间的"3D 娃娃屋"信息架构无法直接放大到 50 间。需要一套**随规模自适应的层次化架构 + 细节分级**。

---

## 2. 关键洞察：规模改变了"看什么"

- **8 间**：细节即信息——谁在打字、屏幕亮不亮、坐姿动作。
- **50 间**：细节是噪音——你要的是**谁在跑 / 谁卡住(红) / 谁在等授权(橙) / 各工具占比**。

> 设计第一性原理：**展示密度随规模反向递减**。拉远时每个 Agent 退化成"一个会变色的状态点"，拉近时才还原成"一间会动的办公室"。

这条原理直接推导出 **LOD（Level of Detail，细节分级）/ 语义缩放** 作为整套架构的骨架——它同时解决**可读性**（50 间不糊成一团）与**性能**（远处不跑骨骼动画）。

---

## 3. 信息架构：四级层次（多数情况坍缩为三级）

```
园区 Campus
  └─ 楼/分区 Building   = 一个 channel（工具）           ← 主题色 = 该工具光环色
       └─ 庭院 Courtyard = ≤8 间房环绕一个中庭休息室      ← 现有这套
            └─ 工位间 Room = 1 个会话(主 agent + 子代理)
```

- **Room 工位间**：1 个会话。主 agent + 子代理、状态色、channel 光环（已实现）。
- **Courtyard 庭院**：≤8 间房 + 1 个中央休息室。**就是今天的实现**，不动。
- **Building 楼 = channel**：装该工具的全部会话。
  - 该 channel **≤8 个** → 1 个庭院（坍缩，等于今天）。
  - 该 channel **>8 个** → `ceil(n/8)` 个庭院，在楼的地块内网格/环形排布。
  - 整楼主题色 = 该 channel 的光环色（复用 `channelHalo()`：claude 橙 / cursor 黑白 / kimi 蓝 / trae 绿 …）。
- **Campus 园区**：所有楼排布在一张地图上，中心可放**总部广场**（全局 KPI / 天气 / 四季底座）。

> 40–50 间分摊到 ~6–8 个工具，多数工具 3–10 人 → 每楼 1–2 个庭院，层级不会爆炸。

## 4. 布局算法（复用现有 ring 数学）

### 4.1 三个尺度，同一套环形/网格函数

现有 `cellPos(i)` / `orderedRingCells(ring)` / `snap90()` 可在多个尺度复用，只是"格距 pitch"不同：

| 尺度 | 单元 | pitch（格距） | 是否旋转朝中心 |
|------|------|---------------|----------------|
| 庭院内 | Room | `STEP = ROOM+PLAZA` | **是**（房间开口朝中庭，现状） |
| 楼内 | Courtyard | 庭院外接尺寸 + 街道 | 否（庭院保持轴对齐，便于总览读） |
| 园区 | Building | 楼外接尺寸 + 主干道 | 否（楼轴对齐，标签/色块正读） |

> 旋转只在**最内层（房间朝庭院）**保留——那是娃娃屋的灵魂；楼和园区层不旋转，保证总览时标签、状态点、色块都正读。

### 4.2 楼内多庭院

一个 channel 有 `n` 个会话：

```
庭院数 k = ceil(n / 8)
楼内用 orderedRingCells / 网格摆 k 个庭院
每个庭院内部 = 现有 ≤8 间 ring 布局
```

### 4.3 园区摆楼

```
楼数 B = channel 种类数（含"未知"兜底桶）
园区用 ring/grid 摆 B 座楼 + 中心总部广场
园区底座 = 覆盖最外楼 + 自适应 viewSize（沿用 buildBase 自适应思路，只是尺度更大）
```

### 4.4 小楼/小庭院的退化

- channel 只有 1–2 人 → 该楼用**紧凑地块**（不展开完整中庭，或中庭缩小/共享），避免"1 个人占一座空庭院"。
- 单 channel、≤8 人（个人使用场景）→ 全坍缩为**今天的单庭院**，零视觉变化。

## 5. LOD 三级（语义缩放）

由相机 `zoom` 阈值驱动（带迟滞 hysteresis 防抖），切换各单元的渲染细节：

| 层级 | 触发 | 园区 | 楼 | 庭院 | 房间 | 角色 |
|------|------|------|----|------|------|------|
| **L0 总览** | 拉到最远 | 全园区 | **色块 tile**：工具图标+名+计数+一排状态点 | 不画细节 | — | 不画 |
| **L1 中景** | 中等缩放 | — | 地块轮廓 | 房间外壳+矮墙+地板色+名牌 | 低模/billboard 静态小人 | **不跑骨骼动画** |
| **L2 近景/聚焦** | 拉近 / 点击某楼 | — | — | 完整中庭 | **完整 3D**：家具+发光屏+休息室 | **骨骼动画+摆臂**（现状） |

- **L0 每楼一个状态条**：N 个小点（每个会话一个），颜色 = 状态色（复用 `LED_COLOR`）；楼框主题色 = channel 光环色。一眼看出"哪栋楼有人卡红 / 等授权橙"。
- **L2 只对"聚焦/最近的庭院"生效**——这是性能闸门（见 §6）。
- 过渡：跨阈值时淡入淡出，避免突变。

---

## 6. 性能策略（40–50 间不掉帧）

全量精渲估算：50 间 × ~5 人 = **~250 个骨骼动画 + AnimationMixer**，加几百件家具 + 阴影 + Bloom → WebGL 必然掉帧。对策：

1. **只有 L2（聚焦/最近）庭院**实例化 skinned clone + 跑 mixer；L0/L1 一律静态。
2. **L0/L1 用 InstancedMesh / Sprite**：状态点、楼色块、低模房间用实例化，几十个 draw call 解决全园区。
3. **视锥剔除 + 按需构建**：只为可见 + 聚焦的单元建细节，移出视野的降级或卸载。
4. **动画角色硬上限**：例如同时只允许聚焦的 1–2 个庭院跑动画（≤16 个角色），其余静态。
5. **复用现有缓存**：`matCache` / `geoCache` 已在，扩展到 LOD 资源。
6. **Bloom 阈值/分辨率**按 LOD 调（总览时降 Bloom 开销）。

> 设计红线：**任意时刻活跃骨骼动画数有硬上限**，与总会话数解耦。

---

## 7. 相机与交互

- **语义缩放**：滚轮缩放跨阈值自动切 L0/L1/L2。
- **点击聚焦**：点某楼/某庭院 → 相机平滑飞入并升级到 L2；返回键回到园区总览。
- **筛选**：按 channel 显隐楼；按状态高亮（只亮 error/waiting）；按 label 搜索定位。
- **总览 KPI**（总部广场 / 顶栏）：总会话数、各状态占比、各工具占比、负载、DGX 状态。
- 现有 `?dbg=1`（XYZ 轴 + 房间配色）、`?rooms=N`（强制 N 间演示）保留，`?rooms` 演示数据要能跨多 channel 生成以测园区。

---

## 8. 数据模型与后端影响

- **channel 成为必需分组键**：全公司接入必须设 `CLAUDE_OFFICE_CHANNEL`（现有链路：hook → `/cc/push` → `/cc/rooms` 透传）。未设的归入 **"未知/其他"兜底楼**，并在文档/接入指南里强调。
- `/cc/rooms` 现有结构（`rooms[].sessionId/label/boss.state/employees/channel/...`）**够用**——分楼在前端按 `channel` 聚合即可，后端无需大改。
- **可选增强**：后端额外返回**按 channel 的聚合计数**（活跃/各状态数），让 L0 总览不必遍历全量；50 间量级下前端实时聚合也 OK，可后置。
- **未来**：若要"按团队/负责人分楼"，需接入额外 metadata（owner/team），本期不做、预留字段。

## 10. 分阶段实施计划

### Phase 1 — 园区骨架（让 50 间不崩、全上屏）
- [ ] 前端按 `channel` 聚合 → 楼 → 庭院的数据分组层。
- [ ] 楼/园区两级布局（复用 `cellPos`/`orderedRingCells`，新增 pitch 参数）。
- [ ] 园区底座 + 相机自适应（扩展 `buildBase` 自适应到园区尺度）。
- [ ] `?rooms=N` 演示数据跨多 channel 生成，验证多楼布局。
- 产出：40–50 间能完整摆出、不裁切、不悬崖（此阶段可仍全精渲，先看布局）。

### Phase 2 — LOD 总览层（保可读 + 保帧率）
- [ ] L0 楼色块 tile（工具图标+名+计数+状态点，InstancedMesh/Sprite）。
- [ ] L1 庭院中景（房间外壳 + 静态小人，关骨骼动画）。
- [ ] 相机 zoom 阈值切换 + 迟滞 + 淡入淡出。
- [ ] 活跃动画硬上限 + 视锥剔除 + 按需构建/卸载。
- 产出：拉远看全局状态、拉近看细节，50 间稳定帧率。

### Phase 3 — 聚焦与筛选（管理视角）
- [ ] 点楼/庭院聚焦飞入，返回总览。
- [ ] 按 channel/状态筛选 + label 搜索。
- [ ] 总部广场 / 顶栏全局 KPI。
- [ ] "未知 channel" 兜底楼 + 接入指南（强调必设 `CLAUDE_OFFICE_CHANNEL`）。

## 11. 风险与开放问题

1. **channel 数据质量**：若大量接入没设 channel，会全挤进"未知楼"，分楼失效 → 需接入规范 + 兜底展示。
2. **单工具人数极不均**：某工具 25 人、某工具 2 人 → 楼大小悬殊，园区排布要能容忍不规则尺寸（楼按各自外接尺寸占地，非等格）。
3. **LOD 切换抖动**：阈值需迟滞 + 实测调参（沿用无头截图验证法）。
4. **性能上限**：极端情况（如聚焦时该庭院 8 间各 5 子代理 = 40 角色）仍可能压力大，动画硬上限要可配。
5. **小庭院空旷**：1–2 人的庭院如何不显空——紧凑地块 vs 共享中庭，待定。
6. **2D 版 office.js**：是否同步这套分楼？本设计先聚焦 3D 版。

---

## 12. 取舍记录（为什么不是别的方案）

- **❌ 单环摊到 50**：一个环放 50 间 → 巨大细长环 + 空旷中庭，房间极小，中庭语义崩。
- **❌ 无限同心方环**：n=9 即"悬崖"（按整个外环定尺寸暴缩）、外环不满偏心、越加越小、内环遮外环。实测见 `/tmp/cc_atrium_param_n9/n12/n16.png`。
- **✅ 按 channel 分楼 + 园区分形 + LOD**：保留庭院美学（用户选定 A 的精神）、规模可扩、退化优雅、帧率可控、且"按工具分楼"本身就是这个看板最有意义的分组维度（用户选定）。
